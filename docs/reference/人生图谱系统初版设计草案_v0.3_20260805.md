# 人生图谱系统初版设计草案

**文档版本：** v0.3  
**日期：** 2026-08-05  
**项目阶段：** 概念设计 / 初步产品定义 / 数据与访问架构补充  

---

## 1. 项目概述

“人生图谱”是一套以个人生命时间为骨架，用于长期记录、整理、展示一个人一生中事件、记忆、照片、文件、人物、地点和未来安排的独立个人信息系统。

系统通过可缩放的时间视图，把人的一生拆分为年、月、日等不同层级，并允许用户从整个人生总览逐步进入某一年、某一月、某一天，查看这一时期留下的事件、记忆和数字资料。

系统不只是传统日记、日历或文件管理器，而是一套：

> **以时间为骨架，连接人生事件、个人记忆和数字资料的生命图谱系统。**

---

## 2. 项目意义

现代人的人生资料通常分散在不同位置：

- 照片和视频保存在手机、相机、硬盘或相册软件中；
- 文档、代码、录音、票据和项目文件分布在不同目录；
- 人生事件存在于日历、聊天记录、笔记或个人记忆中；
- 很多往事只有模糊印象，尚未形成正式记录；
- 未来计划和真正发生的事情之间缺乏连续记录。

这些资料虽然大量存在，却没有一条统一的时间主线将它们连接起来。

人生图谱的价值在于：

1. 直观展示一个人已经走过的生命时间；
2. 通过照片和文件自动重新点亮过去的日子；
3. 允许用户补录已经发生的事件和个人记忆；
4. 支持未来日期的计划与事件安排；
5. 让零散的数字资料逐渐形成完整的人生档案；
6. 帮助用户重新理解不同人生阶段之间的联系；
7. 为长期保存个人及家庭记忆提供独立、可迁移的数据基础。

## 3. 产品定位

### 3.1 核心定位

人生图谱是一款：

- 本地优先；
- 隐私优先；
- API 优先；
- 初始化即加密；
- 可整体迁移；
- 长期使用；
- 时间驱动；
- 可逐步补全；
- 可独立运行；

的个人生命档案桌面应用。

### 3.2 产品副标题

> 每一天都是人生的一格，有些被记住，有些等待被重新发现。

### 3.3 产品边界

系统负责：

- 展示生命时间；
- 保存事件与记忆；
- 建立日期、人物、地点、资料之间的关系；
- 索引用户主动授权的照片和文件目录；
- 自动将资料挂接到对应日期；
- 支持人生、年、月、日多尺度浏览；
- 提供搜索、整理、导出和备份功能。

系统默认不负责：

- 替代操作系统文件管理器；
- 替代专业相册或照片编辑软件；
- 替代完整的网盘；
- 替代复杂项目管理和待办系统；
- 自动扫描未经用户授权的目录；
- 自动复制或移动用户全部文件；
- 擅自把普通文件判断为重要人生事件。

## 4. 产品形态

本项目采用“完整主系统 + 日常轻入口 + 可选扩展组件”的产品结构。

第一阶段建议优先形成：

> **独立桌面主程序 + 浏览器插件日常入口**

桌面主程序负责完整整理和管理，浏览器插件负责每天查看生命进度、快速记录事件与记忆。

## 4.1 独立桌面主程序

桌面主程序是系统的核心载体，负责：

- 人生、年、月、日多尺度图谱；
- 事件、记忆和未来计划管理；
- 公历、农历与双历；
- 资料目录扫描；
- 照片和文件自动挂接；
- 搜索、筛选、总结、备份和导出；
- 本地数据库及权限管理。

桌面应用内部可以采用网页式前端界面，结合本地后台服务，形成以下结构：

```text
桌面应用
├─ 网页式前端界面
├─ 统一 API 客户端
├─ 本地后台服务
├─ 加密数据仓库
├─ 文件与照片索引器
├─ 元数据解析模块
├─ 缩略图缓存
├─ 身份认证与设备授权
└─ 导入、导出、迁移与备份模块
```

这种形态兼具：

- 桌面程序访问本地目录的能力；
- Web 界面展示复杂时间图谱的灵活性；
- 本地数据隐私；
- 为浏览器插件提供统一数据接口；
- 后续扩展移动端和远程访问的可能性。

## 4.2 浏览器插件：日常入口

浏览器插件建议列为项目的重要组成部分，并在桌面核心稳定后尽早开发。

它的意义在于：

- 用户几乎每天都会使用浏览器；
- 可以随时查看当前生命、年度和月度进度；
- 可以快速记录当天事件和个人记忆；
- 可以直接保存网页、截图和选中文字；
- 能显著提高系统的日常可见率和使用频率。

插件不保存完整人生数据库，而是通过桌面主程序提供的本地 API 访问数据：

```text
浏览器插件
      ↓
统一 API：127.0.0.1 / HTTPS 远端地址
      ↓
人生图谱后端服务
      ↓
加密数据仓库
```

桌面主程序未运行时，插件可以：

- 显示最近一次缓存的进度；
- 提示用户启动本地服务；
- 暂存少量待提交记录，并在服务恢复后同步。

### 4.2.1 插件弹出面板

点击浏览器工具栏图标后，显示轻量面板：

```text
今天，是你人生的第 14,xxx 天

人生进度       xx.x%
今年进度       xx.x%
本月进度       xx.x%

今年还剩 xxx 天
本月还剩 xx 天

[记录今天]
[添加记忆]
[添加未来事件]
[打开人生图谱]
```

### 4.2.2 新标签页模式

插件可以选择接管或增强新标签页，显示：

- 当前公历、农历和星期；
- 人生、年度和月度进度；
- 今天是人生第几天；
- 今日事件；
- 未来近期计划；
- 往年今日；
- 快速记录入口。

新标签页不必每次展示完整的三万多个生命格，可以只展示：

- 当前年份；
- 最近十二个月；
- 当前生命阶段；
- 精简生命进度条。

### 4.2.3 网页悬浮进度条

插件还可以提供可选的网页悬浮小条：

```text
人生 38.4% · 今年 59.5% · 本月 16.1%
```

该功能默认关闭，由用户主动开启，并支持：

- 拖动位置；
- 调整透明度；
- 自动隐藏；
- 仅在新标签页显示；
- 指定网站不显示；
- 只显示人生、年度或月度其中一项；
- 隐藏预计剩余时间。

### 4.2.4 浏览器采集能力

插件后续可以支持：

- 保存当前网页；
- 保存网页截图；
- 保存选中文字；
- 保存网页标题、链接和时间；
- 关联某个日期、事件、记忆或人生章节；
- 记录“今天看到了什么”。

浏览器插件是生命图谱的轻量入口和采集器，不承担完整人生图谱的复杂整理工作。

## 4.3 桌面进度条 / 桌面小组件

桌面进度条适合作为可选扩展，而不是唯一入口。

它可以显示：

```text
人生 38.4% ━━━━━━━━━━━━━━━
今年 59.5% ━━━━━━━━━━━━━━━━━━━━━
本月 16.1% ━━━━━
```

点击后可以展开：

- 今日日期与农历；
- 已走过天数；
- 当前年、月剩余时间；
- 今日事件；
- 快速添加事件；
- 快速添加记忆；
- 打开主程序。

桌面小组件的优势：

- 不依赖浏览器；
- 可以开机常驻；
- 适合与系统托盘结合；
- 便于快速查看和记录。

需要注意：

- 桌面经常被其他窗口遮挡；
- 常驻进度可能给部分用户带来压力；
- 需要适配多显示器、系统缩放和全屏应用；
- 应允许自动隐藏、透明度和显示内容设置。

因此产品优先级建议为：

1. 浏览器插件；
2. 桌面托盘快速入口；
3. 桌面进度条或桌面小组件。

## 4.4 移动端或 PWA

移动端不复制桌面端全部能力，主要用于：

- 随手记录当天事件；
- 添加一段记忆；
- 拍照并附加说明；
- 语音记录；
- 查看今天、近期和往年今日；
- 添加未来安排。

移动端可以在桌面核心和浏览器插件稳定后开发。

## 4.5 可选私有同步

后期可以支持：

- 多台电脑同步；
- NAS 或个人服务器部署；
- 家庭成员共同维护；
- 加密云端备份。

以上均不是第一阶段必需能力。


## 5. 核心设计原则

### 5.1 时间是主骨架

所有事件、记忆、照片和文件都尽量通过日期或时间段组织。

### 5.2 大尺度看进度，小尺度看内容

- 人生视图看整个生命进度；
- 年视图看一年的进度和分布；
- 月视图看当月剩余时间和每日内容；
- 日视图查看具体事件、资料和记忆。

### 5.3 已走过的日子与有记录的日子必须分开

一个日期即使没有任何资料，也仍然属于已经走过的人生。

因此每个日期格至少包含两层信息：

1. 时间状态；
2. 内容状态。

### 5.4 自动归档与人工确认并存

系统可以自动识别照片和文件日期，但不能把自动推测当成确定事实。

### 5.5 记忆允许模糊

人的记忆不一定精确到某一天，系统必须支持：

- 精确日期；
- 某个月；
- 某一年；
- 某个时间段；
- 大致年份；
- 某个人生阶段；
- 日期未知。

### 5.6 本地优先、隐私优先

个人生命档案可能包含极高敏感度的信息，系统默认本地运行，未经用户明确授权不得上传外部服务器。

### 5.7 长期可读、可迁移

数据必须支持完整导出，避免被锁死在某个版本或某种软件中。

### 5.8 主系统负责整理，轻入口负责陪伴

完整人生图谱不需要全天常驻，但生命进度与快速记录入口应当自然进入用户每天使用的环境。

因此：

- 桌面主程序负责深度浏览和整理；
- 浏览器插件负责日常查看和快速采集；
- 桌面小组件负责可选常驻展示；
- 移动端负责外出场景的随手记录。

### 5.9 API 是唯一数据访问入口

桌面前端、浏览器插件、未来移动端、远程 Web 页面和资料索引服务均不得绕过后端直接访问数据库。

统一 API 可以保证：

- 本地运行与 VPS 运行使用相同业务逻辑；
- 前端只需切换 API 地址；
- 数据库可以在未来替换而不影响客户端；
- 权限、加密、审计和数据校验集中处理；
- 多设备访问能够使用统一身份体系。

### 5.10 数据从初始化开始即加密

系统不提供“先明文使用、以后再加密”的默认路径。

初始化个人仓库时即创建加密数据库，并生成独立主密钥。后续事件、记忆、设置和正式纳入仓库的附件均在加密体系内保存。

### 5.11 迁移优先于同步

第一阶段优先解决整套数据在不同电脑、本地后端和 VPS 之间的安全迁移。

真正的多设备离线双向同步涉及冲突合并、删除传播、附件版本和密钥分发，应作为后续独立阶段处理。

## 6. 时间尺度与视图体系

系统采用连续缩放的时间结构：

```text
人生总览
   ↓
年度视图
   ↓
月度视图
   ↓
日期详情
   ↓
事件 / 记忆 / 资料详情
```

---

## 7. 人生总览视图

## 7.1 默认生命长度

默认按照 **100 岁** 展示一个人的生命长度。

用户可以选择：

- 80 岁；
- 90 岁；
- 100 岁；
- 120 岁；
- 自定义。

目标年龄仅用于可视化，不代表真实寿命预测。

## 7.2 日期格设计

人生总览中，每一个小格代表一天。

按 100 岁计算，一生约有 36,525 个日期格。

日期格具有以下基础状态：

### 时间状态

- 已过去；
- 今天；
- 未来。

### 内容状态

- 无内容；
- 有事件；
- 有记忆；
- 有照片；
- 有文件；
- 有未来计划；
- 有固定事件；
- 有多类内容。

## 7.3 推荐视觉编码

为避免画面过于杂乱，采用分层表达：

- 格子底色：过去 / 今天 / 未来；
- 中心深浅：当日资料密度；
- 小圆点：有正式事件；
- 柔和边框：有个人记忆；
- 空心标记：未来计划；
- 角标：固定节日、生日或纪念日；
- 强调描边：今天。

## 7.4 生命进度信息

页面顶部可以显示：

- 当前年龄；
- 已走过年数；
- 已走过月数；
- 已走过天数；
- 人生进度百分比；
- 按目标年龄估算的剩余天数；
- 有记录的日期数量；
- 资料覆盖率。

用户可以隐藏“剩余时间”，只显示已经走过的部分，避免产生不必要的心理压力。

## 7.5 日常进度展示策略

由于浏览器插件或桌面小组件可能每天高频出现，默认文案应强调“已经走过”，而不是持续制造倒计时感。

默认推荐显示：

- 今天是人生第几天；
- 人生已走过百分比；
- 当前年度进度；
- 当前月份进度。

以下内容作为可选项：

- 按目标年龄估算的剩余天数；
- 今年剩余天数；
- 本月剩余天数；
- 每日剩余时间。

显示风格可以包括：

- 数字模式；
- 进度条模式；
- 格子模式；
- 圆环模式；
- 温和文案模式；
- 极简模式。

## 8. 年度视图

点击人生总览中的某一年，进入年度视图。

年度视图主要展示：

- 这一年已经过去多少；
- 这一年还剩多少；
- 每一天的内容状态；
- 各月事件和资料密度；
- 当年重要事件；
- 年度照片、文件和记忆统计；
- 年度关键词；
- 年度总结。

当前年度可显示：

```text
2026 年进度：xx%
已过去：xxx 天
剩余：xxx 天
```

历史年度不再显示“剩余时间”，而是显示该年度的完整记录情况。

## 9. 月度视图

点击某个月进入月度视图。

月度视图可以采用传统月历或连续日期格布局。

主要显示：

- 当前月份进度；
- 已过去天数；
- 剩余天数；
- 每日事件、记忆和资料状态；
- 节日、节气、生日和纪念日；
- 当月计划；
- 当月照片和文件。

当前月份可显示：

```text
本月进度：xx%
已过去：xx 天
剩余：xx 天
```

## 10. 公历、农历与双历

系统支持三种历法显示方式：

- 公历；
- 农历；
- 双历。

### 10.1 双历模式

月视图中推荐使用双历：

```text
5
六月廿三
```

公历日期作为主信息，农历日期作为辅助信息。

### 10.2 固定事件

系统可以显示：

- 公历节日；
- 农历节日；
- 二十四节气；
- 用户生日；
- 家人生日；
- 纪念日；
- 忌日或祭日；
- 周期性个人事件。

### 10.3 计算原则

生命进度、年龄和已走过天数统一按公历绝对日期计算。

农历主要用于：

- 日期展示；
- 农历生日；
- 节日与节气；
- 固定事件规则；
- 历史回忆检索。

## 11. 日期格交互规则

## 11.1 点击过去日期

主要用于：

- 查看当天事件；
- 查看当天照片和文件；
- 添加补记事件；
- 添加一段记忆；
- 附加老照片或资料；
- 关联人物和地点。

## 11.2 点击今天

主要用于：

- 记录今天发生的事情；
- 添加照片；
- 写一句话；
- 添加心情或感受；
- 添加当天资料；
- 查看今日安排。

## 11.3 点击未来日期

主要用于：

- 添加未来事件；
- 添加计划；
- 添加预约或行程；
- 添加提醒；
- 添加生日、纪念日或固定事件；
- 查看该日已经存在的固定事件。

未来日期格需要与已经发生的记录有明显视觉区别。

## 12. 未来事件状态

未来事件建议采用以下状态：

```text
计划中
  ├─ 已发生
  ├─ 已完成
  ├─ 已延期
  ├─ 已取消
  └─ 待确认
```

事件日期到达以后，系统可以提示用户确认：

```text
原计划：去京都旅行

[确实发生]
[发生但有变化]
[延期]
[取消]
```

系统应允许同时保留：

- 原计划；
- 实际情况；
- 后续记忆。

## 24. 数据与访问架构目标

数据层需要同时满足以下目标：

1. 后端第一阶段可以完全在本地运行；
2. 后期能够将同一套后端部署到 VPS；
3. 所有客户端统一通过 API 访问；
4. 数据从首次初始化开始即以加密方式保存；
5. 本机可使用 PIN 快速解锁；
6. PIN 不能成为唯一数据库加密密钥；
7. 整套数据可以安全导出、导入和迁移；
8. 文件路径在不同设备间可以重新绑定；
9. 第一阶段不依赖复杂的多端实时同步；
10. 将来更换数据库或增加多用户时，不需要重写客户端。

## 25. API 优先架构

系统采用统一 API 作为所有数据访问入口：

```text
桌面主界面 ─┐
浏览器插件 ─┼──→ /api/v1 ──→ 业务服务 ──→ 加密数据仓库
未来移动端 ─┤
远程 Web端 ─┤
资料索引器 ─┘
```

### 25.1 基本原则

- 前端不得直接连接 SQLite；
- 浏览器插件不得维护独立人生数据库；
- 文件扫描服务不得绕过业务层写数据库；
- 所有写入均经过权限、校验、版本和审计处理；
- API 从第一版开始进行版本化；
- 本地和远程模式保持相同数据结构与接口语义。

### 25.2 初步 API 分区

```text
/api/v1/auth
/api/v1/profile
/api/v1/progress
/api/v1/dates
/api/v1/events
/api/v1/memories
/api/v1/plans
/api/v1/files
/api/v1/sources
/api/v1/chapters
/api/v1/people
/api/v1/places
/api/v1/search
/api/v1/devices
/api/v1/settings
/api/v1/export
/api/v1/import
/api/v1/backup
```

### 25.3 本地运行

```text
桌面界面 / 浏览器插件
          ↓
http://127.0.0.1:<port>/api/v1
          ↓
本地后端
          ↓
本地加密仓库
```

本地服务默认只监听回环地址，不直接开放局域网或公网。

### 25.4 VPS 运行

```text
桌面界面 / 浏览器插件 / 移动端
                  ↓
https://life.example.com/api/v1
                  ↓
Nginx / HTTPS
                  ↓
VPS 后端
                  ↓
VPS 加密仓库
```

迁移到 VPS 后，客户端原则上只需：

- 更换 API 地址；
- 完成远程设备登录或配对；
- 不修改业务代码和数据模型。

```text

仓库位置=VPS

```

适合：

- 浏览器插件跨设备使用；
- 未来移动端接入；

### 26.3 迁移模式

```text

   ↓ 导出一致性快照

   ↓ 导入并验证
```

## 27. 加密数据仓库

系统数据不应只被理解为一个数据库文件，而应定义成完整的加密仓库。

建议目录结构：

```text
LifeGraphVault/
├─ vault.json
├─ lifegraph.db
├─ blobs/
├─ thumbnails/
├─ backups/
└─ runtime/
```

### 27.1 文件说明

- `vault.json`：仓库格式版本、加密参数标识、数据库结构版本和非敏感配置；
- `lifegraph.db`：加密 SQLite 数据库；
- `blobs/`：正式纳入仓库的加密照片、录音和文件；
- `thumbnails/`：可重建的缩略图缓存，可选择是否加密；
- `backups/`：本地一致性快照；
- `runtime/`：临时文件和运行缓存，不作为正式迁移内容。

### 27.2 数据库选择

第一阶段建议采用：

> SQLite + 成熟的透明加密方案（优先评估 SQLCipher 或同类兼容实现）

适用原因：

- 个人使用并发量低；
- 便于整体备份和迁移；
- 本地与单节点 VPS 都容易部署；
- API 层可以隐藏底层数据库实现；
- 将来迁移 PostgreSQL 时客户端无需改变。

### 27.3 仓库数据与外部引用

文件可以采用两种保存方式。

#### 外部引用

文件仍位于用户原目录，系统仅保存：

- 资料源标识；
- 相对路径；
- 文件哈希；
- 元数据；
- 缩略图；
- 日期关联。

外部文件是否加密，取决于用户原存储环境。

#### 纳入仓库

用户可以把重要资料正式收入 `blobs/`：

- 附件内容进行加密；
- 使用内容哈希命名或定位；
- 数据库保存附件关系；
- 迁移包可携带完整内容；
- 原文件可以选择保留或删除。

界面必须明确标识：

- **外部引用：原文件未必由本系统加密**
- **仓库附件：已由系统加密保存**

## 28. 主密钥、PIN 与恢复凭据

### 28.1 PIN 的正确定位

PIN 是当前设备上的快速解锁方式，不直接作为数据库主密钥，也不应作为公网唯一登录凭据。

四位或六位 PIN 组合数量有限，如果直接由 PIN 生成数据库密钥，仓库文件被复制后可能遭到离线穷举。

### 28.2 推荐密钥结构

```text
本机 PIN / 恢复密码 / 恢复密钥
                ↓
       密钥派生与设备安全存储
                ↓
          解锁随机主密钥
                ↓
     解锁数据库、附件与迁移包
```

初始化时：

1. 系统生成高强度随机主密钥；
2. 主密钥用于保护数据库和仓库附件；
3. PIN 仅在当前设备上快速解锁主密钥；
4. 独立恢复密码或恢复密钥用于新设备导入、重置 PIN 和灾难恢复；
5. 更换 PIN 时只重新封装主密钥，不重新加密全部数据。

### 28.3 初始化流程

首次建立个人仓库时设置：

```text
个人档案名称
出生日期
目标年龄
本机解锁 PIN
恢复密码或恢复密钥
自动锁定时间
是否信任当前设备
恢复信息保存确认
```

系统必须提醒用户：

- 忘记 PIN 可以用恢复凭据重设；
- 恢复凭据丢失且无已解锁设备时，系统无法替用户恢复数据；
- 恢复凭据不得与迁移包长期存放在同一位置。

### 28.4 密钥派生

恢复密码和 PIN 的保护材料应使用专门的慢速密钥派生函数，并保存独立随机盐和版本化参数。

具体算法与参数在技术实现阶段确定，文档层面应坚持：

- 不直接使用普通哈希充当密钥；
- 密钥派生参数可升级；
- 旧仓库在解锁后可以迁移到新参数；
- 密钥和密码不写入日志。

## 29. 身份认证与设备授权

### 29.1 本机访问

本地模式下：

```text
输入 PIN
   ↓
解锁仓库
   ↓
创建短期本机会话
   ↓
访问本地 API
```

本地 API 只监听 `127.0.0.1`，并仍然要求会话令牌，避免其他本地页面或进程随意调用。

### 29.2 浏览器插件配对

插件首次接入时使用一次性配对码，由主程序签发独立设备令牌。

插件令牌应当：

- 可撤销；
- 有明确设备名称；
- 具有有限权限；
- 可设置有效期；
- 能查看最后访问时间；
- 不等同于主账户密码。

插件默认权限可以包括：

- 查看生命、年度和月度进度；
- 查看今日摘要；
- 添加快速事件；
- 添加记忆；
- 保存网页资料；
- 打开主系统。

默认不包括：

- 导出整个仓库；
- 修改加密设置；
- 修改恢复凭据；
- 一键清空所有数据；
- 管理其他设备。

### 29.3 VPS 远程登录

公网访问不使用短 PIN 作为唯一身份凭据。

建议采用：

- 独立远程账户密码或通行密钥；
- 登录失败限速；
- 短期访问令牌与可续期会话；
- 设备列表与撤销；
- 可选二次验证；
- 登录与安全操作记录。

PIN 可以继续用于解锁高敏感内容或本地客户端，但不能替代远程认证。

### 29.4 自动锁定

系统可以根据用户设置：

- 主窗口关闭后锁定；
- 空闲一段时间后锁定；
- 系统睡眠后锁定；
- 屏幕锁定后锁定；
- 浏览器插件只保留非敏感进度缓存。

---

## 30. 数据模型的迁移与同步预留

即使第一阶段不做实时同步，核心记录也应从第一天包含：

```text
id                 全局唯一标识
created_at         创建时间
updated_at         最后更新时间
revision           修订版本
created_by_device  创建设备
updated_by_device  最后修改设备
deleted_at         软删除时间
schema_version     记录结构版本
```

### 30.1 全局唯一标识

事件、记忆、计划、附件、人物、地点和人生章节均使用全局唯一 ID，避免不同设备产生重复自增编号。

### 30.2 软删除

重要数据默认采用软删除：

- 用户可以在回收站恢复；
- 迁移和未来同步可以识别删除状态；
- 定期清理时才真正物理删除。

### 30.3 修订版本

每次修改递增 `revision`，用于：

- 乐观并发控制；
- 检测过期编辑；
- 为未来冲突合并提供基础；
- 记录重要内容的修改历史。

## 31. 文件路径的跨设备表示

数据库中不能只保存某台电脑的绝对路径，例如：

```text
D:\照片\家庭\2020.jpg
```

建议采用：

```text
资料源：photos_main
相对路径：家庭/2020.jpg
```

每台设备独立保存资料源映射：

```text
设备 A：
photos_main → D:\照片

设备 B：
photos_main → E:\我的照片

VPS：
photos_main → /data/photos
```

这样迁移后只需要重新绑定根目录。

### 31.1 文件身份

系统应综合使用：

- 资料源 ID；
- 相对路径；
- 文件大小；
- 文件哈希；
- 可选文件系统标识；

识别文件移动、重命名和重复。

### 31.2 外接设备

外接硬盘或网络目录暂时不可用时：

- 不删除索引；
- 标记资料源离线；
- 保留日期和事件关联；
- 设备恢复连接后重新校验。

## 32. 整体迁移包

建议定义独立迁移格式：

```text
我的人生图谱_20260805.lifevault
```

迁移包本身应进行整体加密和完整性校验。

### 32.1 包含内容

```text
manifest.json
encrypted-database
encrypted-blobs
encrypted-settings
schema-version
checksums
key-slots
export-info
```

缩略图可以选择：

- 一起迁移，加快导入后显示；
- 不迁移，在新设备重新生成。

外部引用文件默认不复制进迁移包，除非用户选择“完整便携迁移”。

### 32.2 导出类型

#### 仅核心数据

包含：

- 数据库；
- 设置；
- 事件；
- 记忆；
- 计划；
- 索引关系。

不包含外部原文件。

#### 含仓库附件

在核心数据基础上包含 `blobs/` 中正式纳入仓库的文件。

#### 完整便携包

根据用户选择，把部分外部引用文件复制并加密纳入迁移包。

### 32.3 导入流程

```text
选择 .lifevault
      ↓
输入恢复密码或恢复密钥
      ↓
验证加密完整性
      ↓
检查仓库和数据库版本
      ↓
执行必要升级
      ↓
导入数据及仓库附件
      ↓
重新绑定外部资料源
      ↓
生成新设备凭据
      ↓
完成校验
```

### 32.4 导入策略

导入时支持：

- 创建新仓库；
- 替换当前空仓库；
- 恢复为独立副本；
- 后期增加合并导入。

第一阶段不建议直接把两个可写仓库自动合并。

## 33. 备份与恢复

### 33.1 一致性快照

运行中的数据库不能直接粗暴复制。

备份流程应先创建一致性快照，再进行加密打包。

### 33.2 备份类型

- 手工完整备份；
- 定时本地备份；
- 退出程序时轻量快照；
- 迁移前强制快照；
- 可选远程加密备份。

### 33.3 备份保留

可提供：

- 最近 7 份；
- 每周 4 份；
- 每月 12 份；
- 用户自定义；
- 重要版本永久保留。

### 33.4 恢复验证

备份不能只生成不验证。系统应定期执行：

- 包完整性检查；
- 数据库可解锁检查；
- 结构版本检查；
- 附件哈希检查；
- 恢复演练提示。

## 34. 数据迁移与多端同步的边界

### 34.1 第一阶段：整体迁移

第一阶段支持：

- 本地电脑迁移到另一台电脑；
- 本地仓库迁移到 VPS；
- VPS 仓库导回本地；
- 整体备份恢复；
- 资料源重新绑定。

迁移完成后，明确选择一个主库。

### 34.2 后期：多端同步

真正多端同步需要处理：

- 同一事件被两台设备同时修改；
- 离线新增记录冲突；
- 删除与恢复传播；
- 附件上传中断；
- 文件重复；
- 设备时间不一致；
- 密钥分发与撤销；
- 历史版本合并。

因此同步应作为单独阶段，不与首版迁移功能混在一起。

### 34.3 推荐的过渡模式

在尚未实现双向同步前：

> VPS 作为唯一可写主库，各设备通过 API 访问；本地只保存缓存和加密备份，不同时维护第二个可写数据库。

## 35. VPS 部署与仓库解锁

### 35.1 安全模式

VPS 重启后：

```text
服务已启动
仓库仍锁定
```

管理员通过安全页面或服务器命令输入恢复凭据，主密钥只加载到进程内存中。

优点：

- 服务器磁盘或备份泄露时，仓库仍然加密；
- 重启后不会自动暴露内容。

缺点：

- 每次服务器重启需要人工解锁。

### 35.2 自动运行模式

允许服务账户使用受限的系统凭据或密钥文件自动解锁。

优点：

- VPS 重启后自动恢复服务；
- 更适合长期无人值守。

缺点：

- 服务器被完整控制时，攻击者更容易取得解锁材料。

系统可以让用户在安全性与便利性之间选择。

### 35.3 远程访问要求

- 全程 HTTPS；
- 后端不直接暴露开发端口；
- 通过反向代理访问；
- 登录失败限速；
- 敏感操作重新验证；
- 设备令牌可撤销；
- 数据导出需要高权限确认；
- 记录登录和安全操作日志；
- 数据库与附件目录限制为服务账户访问。

### 35.4 静态加密的能力边界

加密仓库主要保护：

- 关机状态下的数据；
- 被复制的数据库；
- 迁移包；
- 备份文件；
- 丢失的磁盘。

当 VPS 已经解锁并正常提供服务时，后端必须在内存中处理明文数据。若服务器最高权限被完全控制，仅靠数据库静态加密不能继续保证运行中数据安全。

## 40. 主要风险

### 40.1 功能膨胀

系统容易变成相册、文件管理器、日历、待办、网盘、家谱和 AI 助手的混合体。

解决原则：

> 始终保持“时间索引”是核心，其他功能只作为时间图谱的资料来源或查看入口。

### 40.2 PIN 被误当成加密密钥

短 PIN 不能单独保护可被复制的仓库。

解决原则：

- 主密钥随机生成；
- PIN 仅解锁主密钥；
- 设置独立恢复凭据；
- 远程登录使用更强身份认证。

### 40.3 恢复凭据丢失

端到端掌握密钥意味着服务方无法代替用户恢复。

需要：

- 初始化时强制确认；
- 提供打印或离线保存建议；
- 支持多份恢复密钥槽；
- 已解锁设备可重新生成恢复凭据；
- 定期提示用户验证恢复资料。

### 40.4 自动扫描噪声过多

需要：

- 排除规则；
- 文件类型过滤；
- 去重；
- 聚合；
- 资料层与事件层分离。

### 40.5 日期不准确

需要：

- 保存日期来源；
- 显示可信度；
- 支持手工修正；
- 支持大致时间；
- 不强行精确到某一天。

### 40.6 迁移与同步概念混淆

如果本地库和 VPS 库同时可写，很容易产生不可控冲突。

第一阶段必须坚持：

- 一次只选择一个主库；
- 迁移后原库只读或归档；
- 真正双向同步单独开发。

### 40.7 VPS 已解锁状态风险

数据库静态加密无法防御已经完全控制运行服务器的攻击者。

需要：

- 最小权限；
- HTTPS；
- 系统及时更新；
- 手工解锁可选；
- 安全日志；
- 加密备份；
- 限制管理接口。

### 40.8 生命剩余时间带来压力

允许用户：

- 只显示已经走过的日子；
- 隐藏剩余天数；
- 隐藏百分比；
- 自定义目标年龄；
- 使用更加温和的文案。

## 41. 初步技术建议

```text
桌面外壳：Tauri 或其他轻量桌面壳
前端：HTML / CSS / JavaScript，或现代前端框架
后端：Python / Rust / Node.js 本地及 VPS 服务
API：REST / JSON，版本化为 /api/v1
数据库：SQLite + 透明加密实现
身份：本机会话、设备令牌、远程账户体系
密钥：随机主密钥 + PIN 包装 + 恢复凭据

文件监听：系统文件监听接口
元数据：EXIF、媒体信息、Office/PDF 元数据解析
缩略图：本地缓存
迁移格式：加密 .lifevault 包
远程入口：Nginx + HTTPS + 后端服务
```

具体技术选型应先通过以下原型验证：

1. 加密数据库绑定是否稳定；
2. 桌面打包后能否可靠解锁；
3. PIN 更换是否无需重加密全库；
4. 迁移包能否跨 Windows 和 Linux 导入；
5. 浏览器插件能否安全完成本地配对；
6. VPS 重启后的解锁模式是否满足预期；
7. 大量日期格和文件索引性能是否合格。

7. 后期同一后端可以部署到 VPS；
8. 数据库从初始化开始即加密；
9. 初始化时设置本机访问 PIN；
10. PIN 不直接充当数据库唯一主密钥；
11. 同时设置独立恢复密码或恢复密钥；
12. 数据支持整体加密导出和导入；
13. 文件路径使用资料源和相对路径；
14. 第一阶段先实现整体迁移，不做复杂实时同步；
15. 迁移到 VPS 后优先采用单一远程主库。

## 44. 当前结论

人生图谱已经具备较完整、可实施的产品框架。

第一版不应只关注页面和日期格，还必须同时建立可长期延续的数据底座：

> **统一 API、初始化即加密、PIN 快速解锁、独立恢复凭据、设备授权和整体迁移能力。**

这样可以避免项目后期从本地搬到 VPS 时重写前端或重新设计数据库访问方式，也能避免先积累大量明文个人资料后再进行高风险加密改造。

第一版推荐形成：

> **本地运行的加密后端 + 桌面主程序 + 浏览器日常入口。**

当本地版本稳定后，可以将同一套后端和加密仓库迁移至 VPS。桌面端和插件切换 API 地址后继续使用，VPS 成为唯一可写主库。

## 45. 暂定产品定义

> 人生图谱是一套以个人生命时间为骨架，连接事件、记忆、照片、文件和未来计划的本地优先生命档案系统。系统采用统一 API 访问和初始化即加密的数据仓库，支持通过 PIN 在本机快速解锁，并通过独立恢复凭据完成备份、恢复和跨设备迁移。用户可以通过桌面主程序从一生、年份、月份和日期等不同尺度查看已经走过的时间以及每个日子中留下的内容，也可以通过浏览器插件随时查看生命进度、快速记录事件和记忆。后端初期在本地运行，后期可以迁移到 VPS，并由不同设备通过同一套 API 安全访问。
